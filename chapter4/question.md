### 1.本章介绍了三种经典的智能体范式:ReAct、Plan-and-Solve 和 Reflection。请分析:

- 这三种范式在"思考"与"行动"的组织方式上有什么本质区别？
- 如果要设计一个"智能家居控制助手"（需要控制灯光、空调、窗帘等多个设备，并根据用户习惯自动调节），你会选择哪种范式作为基础架构？为什么？
- 是否可以将这三种范式进行组合使用？若可以，请尝试设计一个混合范式的智能体架构，并说明其适用场景。

> **答：**

#### 这三种范式在"思考"与"行动"的组织方式上有什么本质区别？

本质区别在于**"思考(Thinking)"和"行动(Acting)"在时间轴上如何编排**，以及**反馈从哪里来**。

| 范式               | 思考与行动的组织                                          | 反馈来源                                   | 本质                                |
| ------------------ | --------------------------------------------------------- | ------------------------------------------ | ----------------------------------- |
| **ReAct**          | **交错进行**：想一步 → 做一步 → 观察 → 再想一步，单一循环 | **外部环境**（工具返回的 Observation）     | 在线、反应式，边走边看              |
| **Plan-and-Solve** | **先想后做**：一次性规划出完整计划，再按计划顺序执行      | 主要是**内部计划**（执行阶段一般不重规划） | 离线规划 + 顺序执行，思考与行动解耦 |
| **Reflection**     | **做完再评、评完再改**：生成 → 自我批判 → 修订，迭代收敛  | **自身/评审者**（对自己产物的批判）        | 自我监督的迭代优化                  |

逐条对比：

- **ReAct**：思考和行动**紧耦合、交替**。每一次 `Action` 都基于上一步真实的 `Observation`，因此能动态应对未知环境。代价是步步依赖外部反馈，路径不可预知，token 消耗大。对应代码 `ReAct.ts` 里的 `while` 循环。
- **Plan-and-Solve**：把"思考"**前置并全局化**——`Planner` 先把问题拆成 JSON 步骤数组，再交给 `Executor` 逐步执行（`PlanAndResolve.ts`）。规划与执行**解耦**，结构清晰、可控，但执行中途若发现计划有误，一般不会回头重规划（本章实现就是线性执行，不带重规划）。
- **Reflection**：思考被拆成"**执行**"和"**反思/评审**"两种角色。行动不再面向外部环境，而是**面向自己上一轮的产物**做批判与改进（`Reflection.ts` 中 execution / reflection 两类记忆轮替）。它优化的是**单个交付物的质量**，而非与世界交互。

一句话概括：**ReAct 向外探索（与环境交互），Plan-and-Solve 向前规划（先谋后动），Reflection 向内打磨（自我迭代）。**

#### 如果要设计一个"智能家居控制助手"，你会选择哪种范式作为基础架构？为什么？

**以 ReAct 为基础架构**，再按需融合另外两种。

理由——智能家居的核心特征与 ReAct 高度契合：

1. **强环境交互 / 工具调用密集**：控制灯光、空调、窗帘 = 一系列 `Action`（调 API），且每个动作都需要**先查状态、执行后再确认结果**（Observation）。这正是 ReAct 的 Thought→Action→Observation 循环。
2. **状态动态、不可预知**："空调已开但温度未到""窗帘电机卡住"等需要**根据实时反馈调整**，Plan-and-Solve 那种"一次规划到底"的方式难以应对设备执行失败。
3. **指令常常含糊、需澄清**："有点热" → 需要边推理边查传感器决定开空调还是开窗。

但纯 ReAct 不够，应**融合**：

- **复杂联动场景用 Plan-and-Solve**：像"晚安模式"（关灯+锁门+调温+拉窗帘）这种可预先分解的多设备流程，先规划再执行更稳。
- **习惯学习/校验用 Reflection**：对"自动调节策略"做事后反思（"昨晚把温度调到 18℃ 用户半夜起来改了"→ 修正策略），用于持续优化用户偏好。

所以基座是 ReAct（保证实时可控），外层用规划做编排、用反思做学习。

#### 是否可以将这三种范式组合使用？请设计一个混合范式的智能体架构，并说明其适用场景。

**可以，而且现代 Agent 框架基本都是组合体。** 三者解决的是不同维度的问题（规划 / 交互 / 质量），天然互补。

##### 混合架构：Plan → ReAct-Execute → Reflect（带重规划闭环）

```
              ┌─────────────────────────────────────────────┐
              │                                             │
   用户目标 ──▶ [Planner]  ──生成步骤计划──▶ [ReAct Executor] │
   (Plan)       ▲                              │  每步:      │
                │                              │  Thought    │
                │                              │  Action(工具)│
                │                              │  Observation │
                │                              ▼             │
                │                          [Reflector] ──────┘
                └──── 反思认为计划有误 / 失败 → 触发重规划 ────
                                              │
                                     反思通过 ▼
                                          最终结果
```

- **Planner（Plan-and-Solve）**：把长程目标拆成有序子任务，提供全局结构。
- **ReAct Executor**：每个子任务交给一个 ReAct 子智能体，用"思考-工具-观察"循环真正落地执行，应对子任务内的动态性。
- **Reflector（Reflection）**：对每步结果或整体产物做评审——成功则继续，失败/质量不达标则**反馈给 Planner 重规划**或让 Executor 重试，形成闭环。

##### 适用场景

适合**长程、多步、需调用外部工具、且对结果质量有要求**的复杂任务，例如：

- **软件开发 Agent**：规划开发步骤 → ReAct 调用编译/测试工具实现 → 反思测试结果，失败则修复重试。
- **深度研究 / 报告生成**：规划调研提纲 → ReAct 多次检索取证 → 反思查漏补缺并校验引用。
- **复杂运维 / 自动化任务**：拆解操作步骤 → 逐步执行并观察系统反馈 → 反思异常并回滚或重规划。

> 简单任务无需如此重的架构（会增加延迟和 token 成本）：纯查询用 ReAct，可线性分解的用 Plan-and-Solve，单产物打磨用 Reflection 即可。

### 2.在4.2节的 ReAct 实现中，我们使用了正则表达式来解析大语言模型的输出（如 Thought 和 Action）。请思考:

- 当前的解析方法存在哪些潜在的脆弱性？在什么情况下可能会失败？
- 除了正则表达式，还有哪些更鲁棒的输出解析方案？
- 尝试修改本章的代码，使用一种更可靠的输出格式，并对比两种方案的优缺点

> **答：**

#### 当前的解析方法存在哪些潜在的脆弱性？在什么情况下可能会失败？

本章 `ReAct.ts` 的解析逻辑：

```ts
const thoughtMatch = text.match(/Thought:\s*([\s\S]*?)(?=\nAction:|$)/);
const actionMatch = text.match(/Action:\s*([\s\S]*?)$/);
// ...
const match = actionText.match(/^(\w+)\[([\s\S]*)\]/); // 解析 ToolName[input]
```

潜在脆弱性与失败场景：

1. **强依赖固定英文标签**：模型若输出 `思考：`、`**Action:**`（Markdown 加粗）、`Action -` 或多语言变体，正则直接匹配失败，`action` 变成 `null`，流程被迫终止。
2. **`Action:` 贪婪匹配到字符串结尾（`$`）**：如果模型在 Action 之后又附加了解释、下一段 Observation 或多行内容，会被一并吞进 action，导致 `ToolName[...]` 解析错乱。
3. **`(\w+)` 限制了工具名**：`\w` 只含字母数字下划线，工具名若带空格、连字符（如 `Web Search`、`get-weather`）就无法匹配。
4. **`\[([\s\S]*)\]` 的括号匹配不可靠**：
   - `*` 贪婪会匹配到**最后一个** `]`。当工具输入本身含 `]`（如 `Finish[结果是 a[1]=2]`）时，捕获范围出错。
   - 若模型把 Action 包在代码块里，或写成 `Action: Search("query")`（圆括号/引号风格），正则完全匹配不到。
5. **大小写 / 空白敏感**：`Finish` 写成 `finish`、`Action:` 后多个换行等边缘情况都可能漏匹配。
6. **多个 Action**：一次输出多行 Action 时，正则只能模糊地抓一段，行为不可预期。

根因：**用非结构化的自然语言文本承载结构化指令**，而 LLM 输出本身有随机性，正则是一种"事后猜格式"的脆弱契约。

#### 除了正则表达式，还有哪些更鲁棒的输出解析方案？

由弱到强：

1. **结构化 JSON 输出 + Schema 校验**：要求模型输出 JSON，再用 **zod**（本项目已依赖）/ Pydantic 做解析与校验，失败时携带错误信息**让模型重试**（self-healing parser）。
2. **原生 Function / Tool Calling**：用 OpenAI function calling 或 Anthropic tool use，让模型通过 API 的 `tool_calls` 字段返回**结构化参数**，完全绕过文本解析——目前**最鲁棒、最推荐**。
3. **JSON Mode / Structured Outputs**：部分模型支持 `response_format: { type: "json_schema" }`，由服务端**保证**输出符合 schema。
4. **约束解码 / 语法约束（GBNF grammar）**：在解码层面强制输出符合文法，从根上杜绝格式漂移（本地推理常用）。
5. **XML 标签包裹**：让模型用 `<action><tool>Search</tool><input>...</input></action>`，比裸文本更易稳定解析（Anthropic 系模型对 XML 友好），可作为不支持 tool calling 时的折中。

#### 尝试修改代码，使用一种更可靠的输出格式，并对比两种方案的优缺点

下面给出**方案 A：JSON 输出 + zod 校验**的改造示例（项目已装 zod，改动最小、最贴合本仓库）。

**1) 定义 schema 与新提示词**

```ts
import { z } from 'zod';

// 用判别联合表达两类动作：调用工具 / 结束
const ReActStep = z.discriminatedUnion('action', [
  z.object({
    thought: z.string(),
    action: z.literal('tool'),
    tool_name: z.string(),
    tool_input: z.string(),
  }),
  z.object({
    thought: z.string(),
    action: z.literal('finish'),
    final_answer: z.string(),
  }),
]);
type ReActStep = z.infer<typeof ReActStep>;

const REACT_JSON_PROMPT = `
你是一个能调用工具的智能助手。可用工具如下：
{tools}

你必须严格输出**单个 JSON 对象**，不要包含任何额外文字或代码块标记，格式二选一：
1) 调用工具: {"thought": "...", "action": "tool", "tool_name": "Search", "tool_input": "..."}
2) 给出答案: {"thought": "...", "action": "finish", "final_answer": "..."}

Question: {question}
History: {history}
`;
```

**2) 用 zod 解析替换正则，并带重试**

````ts
private parseStep(text: string): ReActStep | null {
  // 容错：剥离可能存在的 ```json fence，截取首个 { 到末个 }
  const cleaned = text.replace(/```json|```/g, '').trim();
  const start = cleaned.indexOf('{');
  const end = cleaned.lastIndexOf('}');
  const jsonStr = start !== -1 && end !== -1 ? cleaned.slice(start, end + 1) : cleaned;

  const parsed = ReActStep.safeParse(JSON.parse(jsonStr));
  return parsed.success ? parsed.data : null; // 失败可把 parsed.error 反馈给模型重试
}
````

主循环里就不再需要 `parseOutput / parseAction / parseActionInput` 三个正则函数，直接：

```ts
const step = this.parseStep(responseText);
if (!step) {
  /* 把校验错误回填 history，让模型修正后重试 */ continue;
}
if (step.action === 'finish') return step.final_answer;
const observation =
  (await this.toolExecutor.getTool(step.tool_name)?.(step.tool_input)) ?? '未找到工具';
```

##### 两种方案对比

| 维度              | 方案：正则解析自然语言（原实现） | 方案：JSON + zod 校验（改造）                     |
| ----------------- | -------------------------------- | ------------------------------------------------- |
| **鲁棒性**        | 低，格式稍变即失败               | 高，结构化 + schema 强约束                        |
| **错误处理**      | 解析失败只能终止/猜测            | `safeParse` 给出明确错误，可**反馈重试**自愈      |
| **类型安全**      | 无，全是字符串切片               | 有，`z.infer` 直接得到 TS 类型                    |
| **嵌套/特殊字符** | `[]` 嵌套、含 `]` 输入易错       | JSON 原生转义，天然支持                           |
| **可扩展性**      | 加字段/工具要改多处正则          | 改 schema 即可                                    |
| **对模型要求**    | 几乎无（任意文本）               | 需模型能稳定产出合法 JSON（较弱模型可能偶尔出错） |
| **可读性/调试**   | 输出像"思维链"，人读友好         | JSON 偏机器友好，思维过程被结构化                 |
| **实现复杂度**    | 简单直接，依赖少                 | 略复杂，需 schema + 容错清洗                      |

**结论**：教学/演示阶段，正则方案直观、便于理解 ReAct 的"文本协议"思想；但工程落地应优先 **原生 Tool Calling**，其次 **JSON + zod 校验并带重试**。核心思路是把"事后用正则猜格式"升级为"事前用 schema 约定格式 + 失败可自愈"。

> **答：**

#### (1) 为 ReAct 添加"计算器"工具

关键点：**不要用 `eval`**（注入风险），用安全的表达式解析。最小实现可借助一个白名单解析器：

```ts
// chapter4/tools.ts 中新增
export function calculatorTool(expr: string): string {
  // 仅允许数字、运算符、括号、小数点、空白
  if (!/^[\d+\-*/().\s]+$/.test(expr)) {
    return `错误：表达式包含非法字符: ${expr}`;
  }
  try {
    // 受限环境下求值（生产建议用 mathjs 等库）
    const result = Function(`"use strict"; return (${expr})`)();
    return `${expr} = ${result}`;
  } catch (e) {
    return `计算错误: ${e}`;
  }
}

// 注册（main 里）
toolExecutor.registerTool(
  'Calculator',
  '一个计算器。当你需要进行精确的数学运算（加减乘除、括号）时使用，输入为一个数学表达式字符串。',
  calculatorTool,
);
```

> 之所以加计算器：LLM 自己算 `(123+456)×789/12` 容易出错，把数值计算"卸载"给确定性工具是 ReAct 的典型价值——**用工具弥补模型的能力短板**。

#### (2) "工具选择失败"的纠错机制

核心思路：**把失败本身变成可反馈的 Observation，并设预算与递进引导**。

- **明确的错误回填**：工具名不存在 / 参数非法时，不要静默 continue，而是把"为什么失败 + 当前可用工具列表 + 正确格式"作为 Observation 写回 `history`，让模型自我纠正（当前代码已部分做到，但提示信息太弱）。
- **连续失败计数**：维护 `consecutiveFailures`，连续 N 次（如 3 次）失败则：① 注入更强的纠正提示（"你已连续选错工具，请仔细对照工具描述重新选择"）；② 触发一次"反思"让模型复盘；③ 仍失败则**降级**为直接 `Finish` 并说明无法完成，或**升级**给人工，避免空转耗尽步数。
- **参数校验前置**：为每个工具定义输入 schema（zod），调用前校验，把校验错误作为结构化反馈返回。

```ts
let consecutiveFailures = 0;
// ...解析到工具调用后：
const fn = this.toolExecutor.getTool(toolName);
if (!fn) {
  consecutiveFailures++;
  const hint = consecutiveFailures >= 3 ? '【警告：你已多次选错工具，请严格对照下表】' : '';
  this.history.push(
    `Observation: 错误，不存在工具 '${toolName}'。${hint}\n可用工具:\n${this.toolExecutor.getAvailableTools()}`,
  );
  continue;
}
consecutiveFailures = 0;
```

#### (3) 工具数量增长到 50~100 个时的优化

当前做法（`getAvailableTools()` 把**所有**工具描述一次性塞进每一步的提示词）会失效，原因：

- **上下文膨胀**：每步都带 100 个工具描述，token 成本与延迟剧增。
- **注意力稀释 / 选择变差**：候选越多，模型选错概率越高。
- **冗余**：99% 的工具与当前子任务无关。

工程优化方向：

| 方案 | 说明 |
| --- | --- |
| **工具检索（Tool RAG）** | 对工具描述做向量化，按当前 query/子任务**语义检索 Top-K**（如 5~10 个）再注入提示词，而非全量。 |
| **分层 / 命名空间分组** | 把工具按业务域组织成"工具箱(Toolkit)"，**两段式选择**：先选类别，再选具体工具。 |
| **路由(Router)** | 一个轻量分类器/小模型先把请求路由到相关工具子集。 |
| **原生 Function Calling + 结构化 schema** | 用 API 的 tools 字段传结构化定义，模型按需调用，减少自由文本解析。 |
| **MCP 风格的工具服务化** | 工具按服务拆分、按需挂载/卸载，动态加载当前会话相关工具。 |
| **描述与缓存优化** | 工具描述精简模板化、可缓存；高频工具常驻、长尾按需加载。 |

一句话：从"**把所有工具都告诉模型**"转向"**只把此刻相关的少数工具检索出来告诉模型**"。

### 4.Plan-and-Solve 范式将任务分解为"规划"和"执行"两个阶段。请深入分析:

- 在4.3节的实现中，规划阶段生成的计划是"静态"的（一次性生成，不可修改）。如果在执行过程中发现某个步骤无法完成或结果不符合预期，应该如何设计一个"动态重规划"机制？
- 对比 Plan-and-Solve 与 ReAct:在处理"预订一次从北京到上海的商务旅行（包括机票、酒店、租车）"这样的任务时，哪种范式更合适？为什么？
- 尝试设计一个"分层规划"系统:先生成高层次的抽象计划，然后针对每个高层步骤再生成详细的子计划。这种设计有什么优势？

> **答：**

#### (1) 动态重规划机制

本章 `PlanAndResolve.ts` 的 `Executor` 是**线性死执行**：计划一旦生成就照单全收，某步失败也不回头。动态重规划要引入"**监控 → 判断 → 重规划**"闭环（业界称 Plan-and-Execute / ReWOO / LLMCompiler 的 replan 思路）：

1. **每步增加校验器(Validator)**：执行完一步后，让 LLM（或规则）判断结果是否符合预期 / 是否失败。
2. **失败时触发 Replanner**：把"原始问题 + 原计划 + 已完成步骤及结果 + 失败原因 + 剩余步骤"喂给一个重规划提示词，**只对剩余部分重新规划**（而非全部推倒）。
3. **重规划预算**：设置最大重规划次数，避免无限循环；超限则降级输出或转人工。

```
plan = planner.plan(q)
while 还有未完成步骤:
    result = executor.executeStep(step)
    if not validator.ok(step, result):       # 监控
        plan = replanner.replan(q, plan, history, 失败原因)   # 动态重规划
        continue
    history.push(result)
```

这本质上是把 Plan-and-Solve 向 ReAct **靠拢**——引入了"观察-调整"的反馈环。

#### (2) 商务旅行预订：ReAct vs Plan-and-Solve

**ReAct（或 ReAct 为主的混合）更合适。** 理由：

- **强步骤间依赖 + 现实不确定性**：机票时间决定酒店入住日期、租车取还时间；而机票可能售罄/改价。这些信息**只有真正去查/订之后才知道**，无法在规划阶段一次性预知。
- Plan-and-Solve 的静态计划是"**闭眼规划**"，一旦"首选航班无票"，整条计划链就崩了，而它不带反馈调整。
- ReAct 的 Thought→Action(查/订)→Observation 循环能**根据真实查询结果动态调整**——这正是该任务需要的。

> 反过来，第 1 章那个"三天卖苹果求和"的题，步骤确定、无外部不确定性，用 Plan-and-Solve 反而更干净。**判据：步骤间依赖强、依赖外部实时反馈 → ReAct；可线性静态分解、确定性高 → Plan-and-Solve。**

#### (3) 分层规划(Hierarchical Planning)的优势

先出"高层抽象计划"（如：①订机票 ②订酒店 ③租车），再对每个高层步骤生成"详细子计划"（订机票 → 查航班/比价/选座/支付）。优势：

- **分治、控制复杂度**：避免一张又长又平的计划在中段"跑偏"，每层提示词更短、上下文更聚焦，规划质量更高。
- **更适合长程任务**：高层稳定、低层灵活，符合人类"先框架后细节"的认知。
- **局部重规划**：某个子计划失败，只需重做**该高层步骤的子树**，不影响其他分支，与上面的动态重规划天然契合。
- **可并行**：相互独立的高层步骤（订酒店 / 租车）可并行展开子计划与执行。
- **可复用**：通用子计划（如"在线支付流程"）可被多个高层步骤复用。

（这与经典 AI 的 HTN——分层任务网络规划——思想一致。）

### 5.Reflection 机制通过"执行-反思-优化"循环来提升输出质量。请思考:

- 在4.4节的代码生成案例中，不同阶段使用的是同一个模型。如果使用两个不同的模型（例如，用一个更强大的模型来做反思，用一个更快的模型来做执行），会带来什么影响？
  -Reflection 机制的终止条件是"反馈中包含无需改进"或"达到最大迭代次数"。这种设计是否合理？能否设计一个更智能的终止条件？
- 假设你要搭建一个"学术论文写作助手"，它能够生成初稿并不断优化论文内容。请设计一个多维度的Reflection机制，从段落逻辑性、方法创新性、语言表达、引用规范等多个角度进行反思和改进。

> **答：**

#### (1) 执行与反思用不同模型（强模型评审 + 快模型执行）的影响

**正面影响：**

- **成本/延迟优化**：生成（高频、量大）用便宜快的模型，反思（少而关键）用昂贵强模型，性价比更高。
- **利用"判断比生成易"的非对称性**：评审一份代码比从零写出更优解更简单，强评审能挖出弱执行者看不到的问题。
- **打破"自我盲区"**：模型很难发现自己**系统性**的错误（同一套权重既写又评，盲点一致）。换一个模型评审能引入**视角多样性**，类似交叉评审。

**负面影响 / 代价：**

- **反馈失配**：强模型给的建议可能超出快模型的能力，弱执行者"听不懂/改不动"，迭代停滞。
- **风格不一致**：两模型的编码习惯/表达风格不同，反复横跳。
- **工程复杂度**：两套配置、两个 key、成本核算更复杂。

> 结论：**"强评审 + 快执行"的 generator–critic 模式总体是有效且常用的**，前提是反馈要具体、可执行，必要时让评审给出"修改示例"而非空泛意见。

#### (2) 终止条件是否合理？更智能的终止条件

当前 `Reflection.ts` 用 `feedback.includes('无需改进')` 字符串匹配 + 最大轮次。**不够稳健**：

- **字符串匹配脆弱**：模型说成"已经很好了/无明显问题"就匹配不到 → 该停不停，浪费轮次甚至死循环到 max。
- **无收敛度量**：不知道每轮到底有没有实质改进，可能在两个版本间**来回震荡**。

更智能的终止条件——让反思**输出结构化评分**而非自然语言判断：

```ts
// 反思者输出 JSON: { score: 0-100, issues: string[], approved: boolean }
```

- **达标即停**：`score >= 阈值` 或 `issues 为空`。
- **收益递减即停**：`本轮score - 上轮score < ε`（改进幅度太小，边际收益不足）。
- **震荡检测**：检测到结果在多版本间循环则停。
- **客观信号锚定（最有效）**：对**代码**这种可验证产物，别只信模型自评——直接**跑测试 / 类型检查 / 性能基准**，`测试全过 && 性能达标` 才终止。把"主观反思"换成"客观验证"，从根上解决终止判断不可靠的问题。

#### (3) 学术论文写作助手：多维度 Reflection 设计

把单一"评审专家"拆成**多个并行的专项评审者**，每个带专属 rubric 与评分，最后聚合：

| 维度 | 评审者角色 | 关注点 / 评分 rubric |
| --- | --- | --- |
| **段落逻辑性** | 论证结构专家 | 论点-论据-结论是否连贯、有无逻辑跳跃、段落衔接 |
| **方法创新性** | 领域资深审稿人 | 与已有工作的差异、贡献是否清晰、novelty |
| **语言表达** | 学术英语编辑 | 用词准确性、句式、可读性、术语一致 |
| **引用规范** | 文献校对 + 工具 | 引用格式、是否有据可查（可接 RAG/文献库**客观校验**，防"幻觉引用"） |

架构：

```
初稿 ──▶ [4个维度评审者并行打分+给意见]
            │
            ▼
        [协调者] 聚合 → 按严重度排序 → 生成统一修改指令
            │
            ▼
        [改写者] 按指令优化 → 新稿 ──┐
            ▲                        │
            └──── 各维度分数均达标? 否则继续 ◀┘
```

要点：**并行多评审 + 加权聚合 + 客观校验（引用）+ 收敛/达标终止**。引用维度尤其要落到工具校验，而非让模型自评。

> **答：**

#### (1) ReAct 提示词 vs Plan-and-Solve 提示词的结构差异

| 对比 | ReAct 提示词 | Plan-and-Solve 提示词 |
| --- | --- | --- |
| 数量/角色 | **单一**提示词 | **两个**角色专用提示词（Planner / Executor） |
| 核心约束 | 强约束**输出格式**：`Thought/Action/Observation`、`{tool_name}[{input}]`、`Finish[...]` | Planner 约束**分解产物**（JSON 步骤数组）；Executor 约束**单步聚焦**（只解决当前步、只输出结果） |
| 是否带工具 | 注入 `{tools}` 列表 | Planner/Executor 通常不直接调工具 |
| 历史/状态 | 每轮回填 `{history}`，驱动循环 | Executor 带 `{plan}+{history}`，但不形成 think-act 循环 |

**这些差异如何服务各自核心逻辑**：

- ReAct 的核心是"**单循环、边想边做、可被解析地调用工具**"，所以提示词必须把输出**钉死成一种可解析的动作协议**，并每轮喂回历史以支撑迭代。
- Plan-and-Solve 的核心是"**规划与执行解耦**"，所以拆成两个角色：Planner 专注"产出结构化全局计划"（强调独立可执行子任务、逻辑顺序、JSON 数组），Executor 专注"**只做当前这一步、别发散**"。提示词的分裂正对应范式的两阶段分裂。

#### (2) 角色设定的影响

把 `Reflection.ts` 的 `REFLECT_PROMPT` 角色从"**极其严格、追求极致性能的评审专家**"改为"**注重可读性的开源项目维护者**"，输出会显著变化：

- 原角色：反馈聚焦**算法复杂度/性能瓶颈**（如"用筛法替代试除法"）。
- 新角色：反馈转向**命名、注释/文档、代码风格、可维护性、贡献规范**，可能对一个 O(n²) 但清晰的实现说"可读性很好，无需改进"。

**总结**：角色设定（persona）是一个**低成本、高杠杆**的行为控制手段——它直接决定模型的**评价标准、优先级、语气和"什么算好"**。同一段代码，换个角色就会被导向完全不同的优化方向。

> 顺带一提：本章 `REFLECT_PROMPT_TEMPLATE` 里写的是"审查以下 **Python** 代码"，但任务其实是 TypeScript，**角色与上下文不一致**也会干扰反思质量——这正说明提示词每个细节都影响行为。

```text
# 示例

**效果**：格式遵循度显著提升、解析失败率下降、收敛更快，并示范了"如何拆解、何时 Finish"的推理风格。**代价**：提示词变长（token↑），且示例若领域单一可能让模型**过拟合**到示例话题。实务上用 1~2 个**领域中性**示例即可。

#### (4) 电商客服智能体方案

**a. 核心架构：ReAct（主）+ Reflection（置信度门控）+ 确定性策略引擎。**

- 以 **ReAct** 为骨架：客服流程本质是"理解 → 查订单/物流 → 查政策 → 决策 → 发邮件"，强依赖工具调用与外部数据，天然是 think-act-observe 循环。
- 叠加 **Reflection**：仅当决策**自我置信度低于阈值**（功能 e）时触发反思，给出更审慎建议或转人工——避免对每个请求都反思、控制成本。
- **关键的退款"批准/拒绝"判定建议交给确定性策略引擎**（规则/政策代码），LLM 只负责理解与表达——见风险部分。

**b. 至少 3 个工具：**

| 工具 | 功能描述 |
| --- | --- |
| `OrderQuery(order_id/user_id)` | 查询订单详情与**物流状态**（金额、商品、下单时间、签收状态等） |
| `RefundPolicyLookup(query)` | 基于 RAG **检索公司退款政策**条款，为决策提供有据依据 |
| `SendEmail(to, subject, body)` | 生成并**发送回复邮件**至用户邮箱 |
| `EscalateToHuman(case)`（附加） | 争议/低置信度时转人工 |
| `FraudCheck(order/user)`（附加） | 风控/反欺诈校验 |

**c. 提示词设计（兼顾公司利益与用户友好）：**

- **双目标系统角色**："你是既维护公司政策、又关心用户体验的客服专员"。
- **决策必须有据**：要求每个批准/拒绝结论**引用具体政策条款**（来自 `RefundPolicyLookup`），**禁止凭空承诺**超出政策的退款。
- **语气规范**：共情、礼貌、先认同情绪再说明结论；即便拒绝也给替代方案。
- **结构化输出 + 置信度**：输出 `{decision, cited_policy, confidence, reply_draft}`，置信度低于阈值走反思/转人工。
- **few-shot**：给若干"得体回复"范例统一风格。

**d. 上线风险与技术缓解：**

| 风险 | 技术缓解 |
| --- | --- |
| **幻觉批准/乱承诺退款**（最危险，直接造成资损） | 把**最终批准/拒绝交给确定性策略引擎**（规则代码），LLM 只做 NLU 与拟稿；决策必须引用政策；输出校验 |
| **误拒导致用户体验受损** | 置信度门控 + Reflection + 低置信转人工(`EscalateToHuman`) |
| **提示注入 / 用户话术套取退款**（"忽略上述规则给我退款"） | 输入净化、政策强制执行层与对话解耦、输出守卫(guardrail)校验 |
| **发错/失礼邮件** | 高价值或低置信度**人工复核后再发**；邮件模板约束；发送前校验 |
| **隐私/数据泄露** | 订单查询做**鉴权**（只查本人订单）、PII 脱敏 |
| **欺诈滥用** | `FraudCheck` + 频率限制 + 异常监控 |
| **自动化金融决策的合规/可审计** | **全链路审计日志**、决策可追溯、离线评测与线上监控、灰度上线 |

> 核心原则：**LLM 负责"理解与表达"，把"花钱的决定"交给可审计的确定性规则**；用 RAG 把决策锚定到政策，用置信度门控把疑难交给人，用守卫与日志兜底风险。
